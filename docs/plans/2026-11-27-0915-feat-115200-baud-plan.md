# 115,200 Baud Speed Option - Plan

## Goal Capsule

- **Objective:** The person can run Claude30 on their SE/30 at 115,200 baud, twice today's fastest speed, by picking it in Settings and setting the WiFi232 and bridge to match. Answers and file transfers arrive faster, and nothing about the 57,600, 38,400 and 19,200 speeds changes.
- **Means:** Ask the Serial Driver for 115K first, and on an SE/30 whose driver refuses, switch the serial chip's clock source after the driver has opened the port, the same switch Apple's SerialDMA driver makes (KTD1, KTD2).
- **Product authority:** The person's request ("add support for baud rate 115200") and their decisions in this session: ZTerm already ran their SE/30 at 115,200, so the hardware and cable can do it, and nothing may risk the hardware (KD1, KD2).
- **Execution profile:** One pull request to `schreibaer/claude30` (U1-U4), then a hardware run by the person (U5). The release files in `/mnt/project-files/release/` are refreshed with the PR, as for earlier features.
- **Stop conditions:** Stop and ask in these cases:
  - The direct clock switch would need to write any serial chip register other than WR4, WR11 and WR14 (for example WR5, which holds DTR and RTS and could hang up the modem), or any value other than the three bytes pinned in KTD2.
  - The direct switch gives garbled text on the real SE/30 at 115,200 while ZTerm on the same machine, cable and WiFi232 setting works.
  - Any approach needs a system patch, an INIT, or a write to PRAM or ROM.
- **Who finishes:** An implementing agent runs `tools/setup-retro68.sh`, builds the 68k app, runs the host tests (`client/tests`) and the bridge tests (`tests/`). The person runs the U5 hardware rows on the real SE/30.

## Product Contract

### Summary

Settings gains a fourth speed, **115,200 baud**. When chosen, Claude30 opens the port at 115,200, the status line says "connected at 115,200", and the link test reports throughput so the speeds can be compared. On a Mac where Claude30 cannot set 115,200, Connect stops with an alert that says so instead of opening the port at the wrong speed. The docs say how to set the WiFi232 (`AT$SB=115200`) and the bridge (`run.sh --baud 115200`) to match.

### Problem Frame

Claude30 tops out at 57,600 baud because that is the fastest rate the classic Serial Driver's configuration word can name (`baud57600 = 0` in Retro68's `Multiverse.h`). Long answers, diffs and ZMODEM-free file reads all queue behind that rate. The person has run ZTerm at 115,200 on the same SE/30, so the limit is in the app, not the machine.

Going faster is not free on this hardware. The SE/30's serial chip interrupts once per character with a 3-byte FIFO, and earlier research found that it can drop bytes at 57,600 when AppleTalk, virtual memory or floppy access hold interrupts off. The bridge's `W` / `!ACK` window protects against buffer overruns but not against the chip itself missing a byte.

### Key Decisions

- KD1. **Driver first, then the chip's clock, and only on an SE/30.** The SE/30's driver very likely refuses the 115K call, which Apple added for the SerialDMA driver on AV and Power Macs, so the chip switch is the only route that delivers the feature on the person's machine. (session-settled: user-approved — chosen over a driver-call-only version that would most likely not work on the SE/30: the person confirmed ZTerm runs their SE/30 at 115,200.) Governs R4, R5.
- KD2. **Software settings only; nothing that outlives a restart.** The person asked that nothing risk the hardware. Clock-source registers are volatile settings that the driver rewrites on the next open and a restart clears. No patches, INITs, PRAM or ROM writes. (session-settled: user-directed — chosen over any approach that changes the System or persistent state: "Don't do anything that would risk the hardware".) Governs R5, R6.
- KD3. **Refuse rather than fall back.** If 115,200 can't be set, Connect stops with an alert. Opening at 57,600 instead would leave the Mac and the WiFi232 at different speeds, which shows up as garbage rather than an explanation. Governs R6.

### Requirements

**Choosing the speed**

- R1. The Settings dialog offers 115,200, 57,600, 38,400 and 19,200 baud, fastest first, and keeps the existing note that the speed must match the WiFi232 and `run.sh --baud`.
- R2. The choice is saved with the other preferences. A preferences file saved by an older build keeps its speed, and an older build reading a file that says 115,200 falls back to 57,600, as it already does for any unknown speed.
- R3. Everywhere the app names the speed (status line, link test, transcript notes) it says "115,200" when that speed is in use.

**Opening the port at 115,200**

- R4. Connect at 115,200 sets the port to 115,200 baud, 8N1, no handshaking, with the same 32 KB input buffer and the same loss detection as the other speeds.
- R5. On an SE/30 whose driver refuses the 115K call, Claude30 sets the speed by switching the serial chip's clock itself, on the chosen port only, and the driver keeps doing all reading, writing and error counting. Disconnecting, or connecting again at another speed, returns the chip to the driver's own settings, and a restart always clears the switch.
- R6. On any other Mac whose driver refuses the 115K call, Connect stops with an alert saying 115,200 isn't available on this Mac and to pick another speed in Settings. The port is left closed.

**Comparing speeds**

- R7. The link test summary adds bytes per second, so runs at 57,600 and 115,200 can be compared.

**Host side and docs**

- R8. The bridge runs unchanged at `--baud 115200`; its pacing stays at about 90% of the line rate.
- R9. `README.md`, `client/README.md` and `tools/emu/README.md` say how to set all three places to 115,200 and back, that it may need AppleTalk and virtual memory off, and that the link test decides whether to use it.

### Success Criteria

- A 60-minute link test at 115,200 on the person's SE/30 reports zero serial errors with AppleTalk and virtual memory off, or the result is recorded in `client/README.md` with the conditions under which it failed.
- The link test's bytes per second at 115,200 is clearly higher than at 57,600. If it isn't, the `W` window is the limit, which is recorded as follow-up work rather than fixed here.

### Scope Boundaries

- 230,400 baud is out. The same chip switch could reach it, but the SE/30 is unlikely to keep up and the WiFi232 docs only go to 115,200.
- PROTOCOL.md, the bridge's code and ZTerm (tty) mode don't change. ZTerm users set 115,200 in ZTerm itself.
- `tools/send-to-mac.sh` keeps its 57,600 advice. ZMODEM at 115,200 is a separate experiment.
- No automatic speed detection or negotiation with the WiFi232.

#### Deferred to Follow-Up Work

- Tuning the bridge's `--window` default if U5 shows the window, not the line, limits throughput at 115,200.
- The direct clock switch on Macs other than the SE/30 (Plus, SE, II family, Classic). Each would need its own hardware check.

## Planning Contract

### Key Technical Decisions

- KTD1. **Driver call first: csCode 115 after a normal SerReset.** `serial_open` configures the port at 57,600 as today, then issues Control csCode 115 (`kSERD115KBaud` in `Multiverse.h`) on both the input and output drivers. Apple's SerialDMA documentation says to make this call "after a normal SerReset call using some other (lower) baud rate". noErr means the driver now runs at 115,200 and nothing else is needed. `controlErr` (-17), the Device Manager's answer from a driver that doesn't know the code, moves on to KTD2 or KTD3. Any other error refuses, because it may mean a broken port rather than an older driver. Implements KD1.
- KTD2. **Direct clock switch on an SE/30: three write registers, nothing else.** After the driver call fails and Gestalt `gestaltMachineType` returns `gestaltMacSE30` (9), Claude30 writes the chosen channel's control register through the address in low memory `SCCWr` (`LMGetSCCWr()`, 0x1DC): WR11 = 0x00 (receive and transmit clocks straight from the RTxC pin, TRxC an input, no crystal oscillator), WR14 = 0x00 (baud rate generator off, the DTR/REQ pin stays DTR, no auto-echo, no loopback, null DPLL command), and WR4 = 0x84 (x32 clock mode, one stop bit, no parity). These registers are write-only, so each write sets all eight bits: WR11 bit 2 (TRxC as an output would drive the HSKi line), WR11 bit 7 (crystal) and WR14 bit 2 (DTR becomes a DMA request and drops) must stay 0. Check the three bytes against the Zilog manual before the first hardware run. The Mac feeds RTxC from its 3.672 MHz clock, so x32 gives 114,750 baud, 0.4% under 115,200, which is well inside what a UART tolerates. This is the switch the SerialDMA notes describe ("the baud rate generator must be bypassed, using the standard 3.672 MHz SCC clock"). WR5 (DTR and RTS), WR3 and the interrupt registers are never touched, so the modem line and the driver's interrupt handling stay as the driver set them. Implements KD1, KD2. (session-settled: user-approved — chosen over driver-call-only: the only route that works on the SE/30's driver.)
- KTD3. **Machine gate, not trial and error.** The direct switch runs only on an SE/30. On any other Mac a refused driver call returns a new app error that `open_port` in `client/src/mac/modem.c` turns into the R6 alert. This keeps the app from writing chip registers on hardware where `SCCWr` might point somewhere else (IOP-based IIfx and Quadras, AV and Power Macs, emulators such as Basilisk II). Implements KD3.
- KTD4. **Register writes are atomic with respect to the driver's interrupt handler.** Each SCC register write is two accesses to the same control port (register number, then value), and the driver's interrupt handler uses the same port. Interrupts are masked to level 7 around each pair, with the CPU status register restored right after, and the SCC's access recovery time is respected between accesses. Retro68 needs a few lines of inline 68k assembly for the status register; there is no Toolbox call for it.
- KTD5. **The speed choice stays an index; the new speed is appended.** `kSpeed115200 = 3` is added after the existing three, so saved preferences keep their meaning and no `PREFS_VERSION` bump is needed. The dialog maps radio items to speeds through a small table instead of the current `kSet57600 + speed` arithmetic, because the new radio sits first on screen but last in the item list.
- KTD6. **The routing decision is portable and host-tested.** The choice between "driver did it", "switch the chip" and "refuse" depends only on the speed, the driver call's result and the machine type. It lives as one small pure function in `client/src/core/` with host tests, and `serial.c` calls it. The register writes themselves can only be tested on hardware.

### High-Level Technical Design

Directional sketch of `serial_open` at 115,200, not code:

```
open .AOut/.AIn (or .BOut/.BIn) as today
SerReset 57600 8N1, SerHShake off, SerSetBuf 32 KB   (as today)
if speed == 115200:
    err = Control(out, 115); Control(in, 115)
    route = speed_route(speed, err, Gestalt('mach'))
    route DRIVER  -> done
    route DIRECT  -> mask interrupts; write WR11, WR14, WR4 on this channel; restore
    route REFUSE  -> close drivers; return kSpeedUnavailable
clear cumulative errors (as today)
```

Closing the port is unchanged: the driver's close resets the channel, and the next open's SerReset rebuilds the baud rate generator settings.

### Assumptions

- The SE/30's ROM serial driver answers an unknown csCode with `controlErr` (-17), not noErr. If it returned noErr, the app would take the driver route and stay at 57,600; the transcript note that names the route (U2) makes this visible in U5.
- The ROM driver's close or next open rewrites WR4, WR11 and WR14 in full, so R5's restore holds. U5's "Disconnect and Connect at 57,600 without quitting" row confirms it.
- The SE/30's ROM serial driver doesn't rewrite WR4, WR11 or WR14 during normal reads, writes and status calls after the port is open. The U5 hardware run confirms this; if a 60-minute run stays at 115,200 without garbling, the assumption holds.
- The SE/30 channel A (modem port) and channel B (printer port) control registers sit at the documented offsets from `SCCWr` (channel A control at +2, channel B control at +0). The implementer confirms these against *Guide to the Macintosh Family Hardware* before the first hardware run.

### Risks & Dependencies

| Risk | Mitigation |
|---|---|
| Wrong register value garbles the link or hangs the app | Volatile setting only; Disconnect, Quit or restart clears it. Only the three bytes pinned in KTD2 are written (stop condition). |
| Dropped bytes at 115,200 | Existing loss detection marks damaged output. The link test decides whether to keep the speed (U5). Docs advise AppleTalk and VM off. |
| Driver's interrupt handler races the two-step register write | KTD4: interrupts masked around each write pair. |
| Basilisk II or other emulators misbehave | KTD3 machine gate: Basilisk reports a non-SE/30 machine, so it gets the R6 alert unless its driver accepts csCode 115. |
| Throughput gain smaller than 2x | Window-limited; measured in U5, tuning deferred. |

### U2. Opening the port at 115,200

- **Goal:** Connect at 115,200 works on the SE/30 and refuses cleanly elsewhere (R4, R5, R6).

- **Approach:** Add the pure routing function (KTD6). In `serial_open`, after SerSetBuf, call it for 115,200 and act on the route; keep the register writes in one static function in `serial.c` with a comment naming the Zilog registers and the source. Add an app error code for "speed unavailable" and an alert text in `open_port` per R6. When the port opens at 115,200, add a transcript note naming the route taken ("driver" or "chip clock"), so U5 can tell a driver that silently ignored the call from a bad register value. Name the Toolbox and low-memory dependencies in the file's header comment as `serial.h` already does (Gestalt, `SCCWr`, inline assembly for the status register).
- **Test scenarios** (`client/tests/test_speedroute.c`):
  - Speed 57,600, 38,400 or 19,200: route is "none" whatever the other inputs are.
  - 115,200, driver call returned noErr: route is "driver" on any machine.
  - 115,200, driver call returned -17, machine type 9: route is "direct".
  - 115,200, driver call returned -17, machine type 11 (IIci), 6 (II) or 0 (Gestalt failed): route is "refuse".
  - 115,200, driver call returned any error other than -17 (for example -28 notOpenErr) on an SE/30: route is "refuse".
- **Verification:** host tests pass; 68k build succeeds; in Basilisk II, Connect at 115,200 shows the R6 alert or connects if its driver accepts csCode 115, and never crashes.
